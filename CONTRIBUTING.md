# ItStepProject


## Технології

- Backend: Node.js / Express
- Frontend: React + Vite
- База даних: PostgreSQL / MongoDB (обрати за потреби)

## Структура репозиторію

```
ItStepProject/
├── backend/     — серверна частина
├── frontend/    — клієнтська частина (React + Vite)
├── docs/        — документація проєкту
├── .gitignore
├── README.md
└── CONTRIBUTING.md
```

---

## Крок 1. Клонування репозиторію

```bash
git clone https://github.com/<ментор>/ItStepProject.git
cd ItStepProject
```

---

## Крок 2. Запуск проєкту

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Відкриється на `http://localhost:5173`.

### Backend

```bash
cd backend
npm install
npm run dev
```

Сервер зазвичай піднімається на `http://localhost:5000` (перевірте в `backend/src/server.js`).

> Перед запуском скопіюйте `.env.example` у `.env` в обох папках (`frontend/` та `backend/`) і заповніть своїми значеннями:
> ```bash
> cp .env.example .env
> ```

## Крок 3. Правильна робота з гілками

> ℹ️ Для команди `git switch` потрібен Git версії 2.23+. Перевірити: `git --version`.

### 3.1. Перехід у develop

Уся розробка стартує від гілки `develop` (не від `main`!):

```bash
git switch develop
git pull origin develop
```

Якщо гілки `develop` немає локально:
```bash
git switch -c develop origin/develop
```

### 3.2. Створення власної гілки

Гілка створюється **тільки від develop**, за чітким шаблоном назви:

```
feature/<ваше-ім'я>-<backend|frontend>
```

Приклади:
```bash
git switch -c feature/ivan-backend
git switch -c feature/olena-frontend
```

Для окремої дрібної задачі можна деталізувати назву:
```bash
git switch -c feature/ivan-backend-auth
git switch -c feature/olena-frontend-navbar
```

> ⚠️ Ніколи не працюйте напряму в `main` або `develop` — тільки у власній гілці `feature/...`.
> ⚠️ Одна гілка = одна задача/фіча. Не змішуйте кілька непов'язаних завдань в одній гілці.

### 3.3. Робота в гілці

```bash
git status
git add .
git commit -m "feat(backend): додано ендпоінт реєстрації користувача"
```

**Формат повідомлень коміту:**

| Префікс | Коли використовувати |
|---|---|
| `feat:` | нова функціональність |
| `fix:` | виправлення бага |
| `docs:` | зміни в документації |
| `refactor:` | покращення коду без зміни поведінки |
| `test:` | додавання/оновлення тестів |
| `chore:` | технічні зміни (конфіги, залежності) |

### 3.4. Пуш гілки на GitHub

```bash
git push origin feature/ivan-backend
```

Якщо гілка пушиться вперше:
```bash
git push --set-upstream origin feature/ivan-backend
```

## Крок 4. Як докинути свій код у проєкт (Pull Request)

1. На GitHub з'явиться підказка **"Compare & pull request"** біля вашої гілки — натисніть на неї (або вручну: **Pull requests → New pull request**).
2. Виставляєте: **base:** `develop`, **compare:** `feature/ivan-backend`.
3. Заповнюєте опис: що зроблено, як перевірити.
4. Призначаєте ментора як **Reviewer**.
5. Після схвалення — **Merge pull request** (**Squash and merge** — для чистої історії в develop).
6. Видаляєте гілку після мержу:
   ```bash
   git branch -d feature/ivan-backend
   git push origin --delete feature/ivan-backend
   ```

### Як develop потрапляє в main

Коли частина функціоналу в `develop` стабільна й перевірена, ментор створює Pull Request `develop → main` (звичайний **Merge**, без Squash — щоб зберегти історію комітів усіх студентів).

## 🚫 Рекомендації, щоб уникати конфліктів

### 1. Синхронізуйтесь з develop щодня, а не раз на тиждень

```bash
git switch develop
git pull origin develop
git switch feature/ivan-backend
git merge develop
```

Чим довше гілка "живе" без синхронізації — тим більше шансів на конфлікт.

### 2. Одна людина — одна зона відповідальності у файлі

Домовтесь із ментором/командою, хто за який компонент/модуль відповідає. Якщо двоє одночасно редагують один і той самий файл (наприклад, `App.jsx`) — конфлікт майже гарантований.

### 3. Дрібні та часті коміти й PR замість одного величезного

PR на 20 файлів складно рев'ювати й ще складніше мержити без конфліктів. Краще 3-4 маленькі PR, ніж один величезний раз на два тижні.

### 4. Не редагуйте файли, які не стосуються вашої задачі

Якщо бачите зайву помилку в чужому файлі — краще повідомте автора або створіть окремий PR з `fix:`, а не правте "заодно" у своєму PR з іншою фічею.

### 5. Перед стартом нової задачі — завжди свіжий `develop`

```bash
git switch develop
git pull origin develop
git switch -c feature/ivan-new-task
```

Ніколи не створюйте нову гілку від старої локальної копії `develop`.

### 6. Використовуйте `.gitignore` правильно

Не комітьте `node_modules/`, `.env`, `dist/`, `build/` — вони індивідуальні для кожного комп'ютера і провокують "фальшиві" конфлікти.

### 7. Якщо конфлікт все ж стався

```bash
git status
```
Git покаже файли з конфліктами (позначені `<<<<<<<`, `=======`, `>>>>>>>`). Відкрийте файл, оберіть/об'єднайте потрібний код вручну, видаліть маркери конфлікту, після чого:

```bash
git add .
git commit -m "merge: вирішено конфлікт у файлі App.jsx"
git push origin feature/ivan-backend
```

> 💡 Якщо не впевнені, як правильно об'єднати код — краще звернутись до ментора чи автора протилежних змін, ніж видаляти чужий код навмання.

### 8. Спілкування — найкращий засіб проти конфліктів

Перед початком роботи над великою зміною (наприклад, зміна структури папок чи спільного компонента) — попередьте команду в чаті. Технічний конфлікт коду часто починається з відсутності комунікації.

## ✅ Чек-лист перед створенням Pull Request

- [ ] Код працює локально без помилок (`npm run dev` запускається)
- [ ] Гілка синхронізована з `develop` (немає конфліктів)
- [ ] Коміти мають зрозумілі повідомлення
- [ ] Немає зайвих файлів (`node_modules`, `.env` не потрапили в коміт)
- [ ] Додано опис у Pull Request

## Гілкова стратегія проєкту

| Гілка | Призначення |
|---|---|
| `main` | стабільна версія проєкту (захищена, прямий пуш заборонено) |
| `develop` | робоча гілка, куди зливаються всі готові фічі |
| `feature/<ім'я>-backend` | гілка студента для розробки бекенду |
| `feature/<ім'я>-frontend` | гілка студента для розробки фронтенду |
